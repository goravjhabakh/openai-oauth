# v0.6 — Developer Experience and Pre-v1 Hardening

## Goal

Validate `@goravjhabakh/openai-oauth` as an installed dependency in a fresh Node.js
consumer application and remove friction that prevents it from feeling like a
normal Vercel AI SDK provider. This version hardens the already implemented
OAuth, provider, streaming, tools, structured-output, and rich-input surfaces;
it does not expand the set of supported OpenAI models, protocol features, or
input encodings.

The reference experience is a consumer who is familiar with
`@ai-sdk/openai`: install the package, configure OAuth deliberately, select a
model available to their account, and use that model with standard AI SDK APIs
without depending on repository internals or undocumented behavior.

## Scope

### Fresh consumer-app validation

- Create and retain a small, independent fixture application outside the
  package source/test imports. It must install the packed tarball, not import
  `src/` or link the workspace package.
- Validate the supported Node.js version and a clean `pnpm install`, then run
  type-checking and representative executable examples against the package's
  emitted JavaScript and declarations.
- Include an offline/mock path for repeatable CI plus an opt-in account-backed
  path using a consenting account. The live path must keep credentials, host
  IDs, authorization URLs, request bodies, model output, and request IDs out
  of source control and test logs.
- Inspect the generated npm tarball before the fixture installs it. Confirm
  that it contains only the intended runtime files, declaration files, README,
  and package metadata, and that it has no source, credentials, fixtures, or
  development-only artifacts by accident.

### Public API ergonomics

- Review the root entrypoint from the consumer fixture. Keep the normal path
  concise: `createOpenAIOAuth(options)`, `provider.auth`, and
  `provider(modelId)`/`provider.languageModel(modelId)`.
- Make required application-owned configuration clear and hard to misuse:
  actual `agentName`, stable opaque `hostId`, credential-store location/key,
  and an `openAuthorizationUrl` implementation. Validate obvious invalid
  values at the boundary with actionable local errors where practical.
- Review public names, option shapes, return types, comments, and error types
  for consistency with AI SDK terminology. Avoid exposing internal Responses
  transport or OAuth implementation details solely because they are convenient
  internally.
- Confirm the public provider is structurally usable wherever a
  `LanguageModelV4` is expected, without casts or imports from internal paths.
- Preserve the one-package boundary. Add a subpath export only if the consumer
  fixture establishes a concrete need and its ownership, types, and long-term
  compatibility are clear.

### Authentication and model-selection UX

- Provide a complete, copyable sign-in lifecycle: create/persist a host ID,
  configure a private credential file, open the authorization URL, call
  `signIn()`, list models, use a selected model, and call `signOut()` when
  appropriate.
- Explain that `agentName` identifies the consuming application, not this
  library; the app owns the host ID and credential path; and the loopback
  callback needs a local browser and `127.0.0.1` access.
- Make the unauthenticated, expired/rotated credential, revoked credential,
  unavailable-browser, callback, and sign-out paths understandable from errors
  and documentation. Do not introduce automatic reauthorization or silent
  fallback billing.
- Document model discovery as account-aware and dynamic. Examples must call
  `listModels()` or `listModelCatalog()` and must not present a hard-coded model
  as a package default or entitlement guarantee.
- Reconcile catalog capability states and README claims with the capabilities
  that are already fixture/account-backed validated. A capability catalog must
  never overstate support; unknown remains unknown. This work may correct
  metadata or documentation, but it must not turn unvalidated model behavior
  into a new supported capability.

### AI SDK usage coverage

Build runnable, typed examples and consumer-level tests for the existing
validated surface, using dynamic model selection except where an exact
model-gated behavior must be demonstrated:

- **Generation and streaming:** `generateText()` and `streamText()`, including
  reading `textStream`, cancellation/abort behavior, terminal usage, response
  metadata, and the fact that generation aggregates a mandatory Responses SSE
  stream.
- **Reasoning:** the sole supported provider option,
  `providerOptions['openai-oauth'] = { effort: 'medium' }`, only with
  `gpt-5.6-terra`. Show the exact limitation and a preflight/catalog check;
  do not imply that generic AI SDK reasoning settings, other effort values, or
  visible reasoning text work.
- **Tools:** a client-executed AI SDK function tool, its supported tool-choice
  modes, streamed/aggregated tool-call results, and a follow-up result turn
  with complete history. Keep examples within the validated top-level function
  representation and text/JSON tool results.
- **Structured output:** the installed AI SDK v7 `Output.object()` path through
  `generateText()` and `streamText()`, including the strict JSON-schema
  requirement and the `gpt-5.6-terra` gate. Do not promote deprecated
  structured-output APIs as the primary path.
- **Rich input:** supported user PNG and `text/plain` URL/inline file forms on
  `gpt-5.6-terra`, with safe placeholder inputs. State the rejected media,
  provider-reference, upload, and unsupported-history forms next to the
  examples.

Examples must distinguish deterministic local validation failures from
account/model entitlement failures and must not require consumers to copy
secrets, a real host ID, or an authorization URL from documentation.

### Errors and misconfiguration

- Establish and test a consumer-facing error contract for `OpenAIOAuthError`:
  message, `status`, `code`, `param`, `requestId`, and retry guidance where
  available. Preserve redaction and never put token, identity, authorization
  URL, request-body, or tool-input data in errors or logs.
- Exercise representative local failures: missing/invalid provider setup,
  not signed in, unsupported generic options/warnings, invalid model-gated
  reasoning/structured-output/rich-input requests, invalid tool choice, and
  invalid tool-result history.
- Exercise mocked and, where safely possible, live remote failures: admission
  errors, terminal SSE failure/incomplete events, premature EOF, cancellation,
  refresh failures, and plan eligibility/usage/policy errors. Verify status,
  code, parameter, request ID, redaction, and retry guidance survive the
  AI SDK call path.
- Document recovery decisions precisely: when a caller should correct input,
  back off, sign in again, or direct the user to plan/usage settings. Do not
  promise retries, reauthorization, or error-code stability that the upstream
  preview does not provide.

### Package exports and types

- Validate `package.json` export conditions, ESM import behavior, `main`,
  `types`, Node engine range, peer dependency range, and generated `.d.ts`
  files from a separate TypeScript consumer.
- Verify every documented root import is exported at runtime and in types:
  provider factory/types, auth class/options, credential store/types, model and
  capability types, and `OpenAIOAuthError`.
- Prevent accidental public API changes with compile-time export/type tests and
  package-install smoke tests. Use semantic versioning deliberately: do not
  remove, rename, or narrow documented exports in this pre-v1 hardening pass
  without an explicit migration note.
- Ensure consumers do not need to import internal source/dist paths, rely on
  transitive dependencies, or add undeclared type packages.

### README and examples

- Update the README to describe the current implemented v0.5 surface rather
  than its earlier v0.3-era limitations. Keep the preview, local/open-source,
  hosted/commercial, public-route, and no-fallback-billing boundaries prominent.
- Organize documentation around an end-to-end quick start followed by focused
  examples for model discovery, generation, streaming, reasoning, tools,
  structured output, rich input, credential storage, sign-out, and errors.
- Make each example use the actual public package API and verify it in the
  fresh consumer fixture. Clearly label model-gated examples and unsupported
  variants.
- Document package installation and peer dependencies for a normal consumer,
  as well as local-repository development until publication. Do not claim npm
  availability until the package has actually been published.
- Keep `docs/project.md`, `docs/roadmap.md`, `docs/architecture.md`, and
  `docs/research.md` consistent with final verified behavior. Record new
  account-backed observations in research without secrets or personal data.

### Regression testing and release hardening

- Expand unit and fixture tests around public behavior rather than only private
  request conversion: exports, declarations, configuration validation, auth
  lifecycle boundaries, catalog semantics, warnings, errors, metadata, and all
  currently supported AI SDK invocation paths.
- Retain protocol-level tests for request exactness and SSE mapping, especially
  terminal success/failure, tool calls, structured output, rich inputs,
  cancellation, and premature EOF. Test generate and stream parity where both
  APIs support a feature.
- Add a release-oriented command or documented CI sequence that runs format
  checks if configured, type-checking, unit/fixture tests, build, package
  inspection, and fresh-consumer smoke tests. Keep live validation opt-in and
  separate from ordinary CI.
- Regression-test that unsupported capabilities still fail or warn explicitly;
  hardening must not silently forward unsupported fields or broaden support.

## Explicit non-goals

- New model capabilities, additional model-specific validations, a static model
  list/default, or broadening supported reasoning values, tools, schemas, media
  types, file forms, or tool-result forms.
- Browser/runtime portability, a browser OAuth callback flow, remote/hosted or
  commercial deployment support, device-code authentication, or changes to the
  documented public OAuth flow.
- OAuth lifecycle feature expansion such as automatic reauthorization,
  background refresh scheduling, cross-process locking redesign, keychain
  integration, multi-account UX, retries, quota management, or billing
  fallback.
- Private ChatGPT/Codex routes, Codex CLI integration, persistent Responses
  conversations, file uploads, provider-hosted tools, web search, audio/video,
  image generation, or full `@ai-sdk/openai` parity.
- A new package split, a broad abstraction layer, or dependency additions that
  are not necessary to validate/package the existing public surface.

## Completion criteria

v0.6 is complete when a clean Node.js consumer can install the packed package,
type-check and run its documented public API, authenticate deliberately, select
an account-visible model, and use every currently validated feature through
standard AI SDK APIs with accurate limitations. The README/examples, runtime
exports, declarations, capability catalog, warnings, and error guidance must
agree with that verified behavior.

The release gate includes repeatable offline consumer/package regression tests,
an inspected tarball, and opt-in sanitized account-backed validation for the
existing feature set. All unsupported or unvalidated behavior remains explicitly
unavailable; no v0.6 completion claim depends on adding a model capability.

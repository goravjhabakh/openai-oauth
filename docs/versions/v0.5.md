# v0.5 — Richer Inputs and Structured Output

## Goal

Add narrowly verified structured output, image input, and file input to both
`generateText()` and `streamText()`. Preserve the OAuth route invariants:
public `/v1/responses`, complete history, `store: false`, and `stream: true`.
Every new request mapping is gated on sanitized, account-backed fixtures for the
selected model; a listed model is not an entitlement guarantee.

## Scope

### Structured output

- Support the installed AI SDK v7 structured-output surface through
  `generateText()`/`streamText()` and `Output.object()` (not the deprecated
  `generateObject()`/`streamObject()` APIs).
- Convert the provider's `responseFormat: { type: 'json', schema?, name?,
  description? }` only to the exact Responses JSON-schema representation
  accepted on the OAuth route. Validate that the JSON Schema is serializable
  before sending it; invalid schema/options fail locally rather than being
  silently dropped.
- Confirm the accepted request fields, whether a schema name/description is
  required, completion behavior, and streamed JSON event sequence before
  exposing this feature. Until then, retain the existing unsupported
  `responseFormat` warning.
- Keep the existing text aggregation and terminal-success rules. The AI SDK
  performs result validation; the provider must not claim schema conformance
  from a syntactically JSON-looking text response alone.

### Image and file input

- Convert AI SDK v4 user `file` parts only after validating their exact
  Responses encoding. Images are file parts whose media type is `image/*`.
- Test image URL and inline image data separately. Test inline file data/text,
  URL-backed files, and provider references separately; support only the forms
  accepted by the public OAuth route for the tested model.
- Preserve media type and optional filename when the validated protocol
  representation supports them. Reject unsupported media types, data forms,
  and assistant/tool-history file parts before the request; do not coerce them
  to text or upload them.
- The package does not use the unsupported Files upload API. Callers must
  provide data, a reachable URL, or an already-valid provider reference where
  that input form has been validated.

### Metadata and capabilities

- Update the account-aware capability catalog only with per-model validated
  evidence for `jsonSchema`, `images`, and `files`; otherwise retain `unknown`.
- Preserve the already implemented safe response metadata: response ID, model,
  timestamp, terminal status, headers/request ID where received, and terminal
  usage. Reasoning-token presence remains metadata only for the existing
  validated `gpt-5.6-terra` medium-effort path.
- Do not add reasoning text, source/citation parts, source metadata, detailed
  usage fields beyond received terminal usage, or inferred capability claims:
  none has been validated for this release scope.

## Validation and testing

1. With a consenting account, capture redacted fixtures for one successful and
   one rejected JSON-schema request, including its full SSE sequence and
   terminal response. Record the accepted payload and any model restrictions in
   `docs/research.md`.
2. Capture separate redacted fixtures for image URL, inline image, inline file,
   URL file, and provider reference attempts. Record media type, size/encoding
   limits if returned, accepted/rejected forms, request IDs, and model used;
   never retain credentials or user file contents.
3. Unit-test prompt conversion, local input/schema validation, media-type and
   data-form rejection, request-body exactness, capability states, and warning
   parity between generation and streaming.
4. Fixture- and mocked-integration-test structured generation/streaming,
   malformed JSON, schema-validation failure, admission failure, terminal
   failure, cancellation, and premature EOF. Test mixed text/file ordering and
   full-history behavior only when fixtures establish it.

## Explicit non-goals

- Files upload, audio/video input, image generation, file search, Code
  Interpreter, native computer use, hosted MCP/connectors, web search, or
  persistent Responses state.
- Unvalidated image/file encodings, model-specific capability inference,
  automatic file download/upload, or conversion of unsupported input to text.
- Reasoning summaries/text, citations or source metadata, new provider metadata
  claims, parallel tool behavior, retries/fallback billing, browser support, or
  OAuth lifecycle changes.
- Full `@ai-sdk/openai` parity.

## Completion criteria

v0.5 is complete when the provider supports only fixture-proven JSON-schema
output and image/file input forms in both generation paths, validates or
rejects unsupported forms deterministically, and reports only verified safe
capabilities and metadata. Anything not established by account-backed evidence
remains unavailable with an explicit error or warning.

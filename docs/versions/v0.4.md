# v0.4 — Tool Calling

## Goal

Add client-executed AI SDK function tools to `generateText()` and `streamText()`
without relaxing the OAuth route constraints: public `/v1/responses`, complete
history on every request, `store: false`, and `stream: true`. This release is
gated on sanitized, account-backed tool fixtures; current implementation and
research deliberately treat tools as unsupported.

## Scope

### Function tools and tool choice

- Convert AI SDK function-tool definitions and their JSON Schemas to the one
  Responses function-tool representation proven on the direct OAuth route.
  The ordinary top-level representation, namespaced tools, and
  `additional_tools` are alternatives to test, not interchangeable formats to
  forward speculatively.
- Map only verified AI SDK tool-choice modes and named-function selection. An
  unsupported or invalid choice must fail before the request or yield the same
  explicit unsupported warning in generate and stream paths; it must not be
  silently changed to automatic choice.
- Preserve the existing warning behavior for non-function/provider-hosted
  tools until separately verified.

### Tool-call and result mapping

- Map a completed Responses `function_call` to an AI SDK `tool-call` with the
  model's `call_id` as `toolCallId`, its name as `toolName`, and its serialized
  arguments as `input`. Do not substitute the Responses output-item ID: a
  subsequent `function_call_output` is paired by `call_id`.
- Convert AI SDK history containing a tool call and its result to the complete
  Responses input required for the next turn, including the original function
  call and a matching `function_call_output`. Preserve call IDs, ordering, and
  serialized result semantics; do not use `previous_response_id` or item
  references for client-executed function calls.
- `doGenerate()` must aggregate all function calls from its mandatory SSE
  response into its `content`, alongside any text, with the same finish,
  usage, warnings, metadata, and error rules as v0.2/v0.3.

### Streamed arguments

- On a function-call output item, retain its name and `call_id`; append each
  `response.function_call_arguments.delta` by its item ID. Emit AI SDK
  `tool-input-start`, ordered `tool-input-delta` parts, and `tool-input-end`.
- On `response.function_call_arguments.done` (or the completed output item
  when validated as equivalent), emit one AI SDK `tool-call` using the final
  argument string. Do not parse, validate, execute, or expose a partial JSON
  value as a completed call.
- Support interleaved text and tool events in received order. Do not claim
  parallel function calls until an account-backed fixture proves their request,
  stream identity, result pairing, and next-turn behavior.

### Multi-step usage

- Support AI SDK-managed multi-step function-tool use only after the first
  tool-call/result turn is proven end-to-end. Each follow-up request must carry
  the full converted history, including every prior client function call and
  result, because OAuth requests cannot use persistent Responses state.
- The provider executes no tool itself. The AI SDK/application executes the
  function, supplies its result on the next step, and retains normal caller
  controls over whether another step is allowed.

## Validation and testing

1. With a consenting account, capture sanitized fixtures for a function-tool
   request, every accepted tool-choice mode, a streamed argument sequence,
   final call IDs/names/arguments, a result follow-up, and a complete
   multi-step exchange. Record the accepted request representation, event
   fields, request IDs, and rejected variants in `docs/research.md`.
2. Unit-test schema/tool-choice validation, request conversion, tool-call and
   result-history conversion, call-ID versus item-ID pairing, argument-delta
   ordering, incomplete/malformed arguments, and generate/stream warning
   parity.
3. Fixture- and mocked-integration-test `generateText()` and `streamText()`
   for a call-only response, text plus calls, multiple calls only when live
   validated, result continuation, cancellation, admission failures, terminal
   failures, and EOF before completion. Assert that fixtures, errors, and
   metadata never contain credentials or sensitive tool input/output.

## Explicit non-goals

- Provider-executed, hosted, MCP, web-search, computer-use, code-interpreter,
  custom, or `tool_search` tools.
- Unvalidated top-level/namespaced/`additional_tools` encodings, tool-choice
  variants, parallel calls, or tool-result output schemas.
- Persistent Responses conversations, `previous_response_id`, automatic
  retries/fallback billing, browser support, or OAuth lifecycle changes.
- Structured output, rich inputs, and full `@ai-sdk/openai` parity.

## Completion criteria

v0.4 is complete when a caller can use a verified AI SDK function tool through
both generation paths, receive correctly identified streamed and aggregated
calls, return matching results in a later complete-history request, and run a
verified multi-step exchange. Everything not established by the required
fixtures remains unavailable with an explicit error or warning.

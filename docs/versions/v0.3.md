# v0.3 — Provider Features

## Goal

Make the OAuth provider more transparent and predictable without expanding into
tools, structured output, or rich inputs. Add a narrow, verified reasoning
control, account-aware capability reporting, provider metadata, precise warnings
for omitted options, and consistent actionable errors for both `generateText()`
and `streamText()`.

v0.1/v0.2 behavior remains the baseline: public `/v1/responses` only, complete
history, `store: false`, mandatory `stream: true`, and client-side aggregation
for `generateText()`.

## Scope

### Reasoning and provider options

- Add a documented `providerOptions['openai-oauth']` surface for only the
  reasoning controls proven by sanitized, account-backed fixtures (for example,
  an effort and/or summary value if accepted by the direct OAuth route).
- Validate the option values locally and send only their verified Responses
  request representation. Do not forward AI SDK's generic `reasoning` setting
  as an undocumented substitute.
- Return reasoning output and reasoning-token usage only when the stream
  supplies them and the AI SDK v4 contract can represent them. Never synthesize
  reasoning text, token counts, or a provider default.
- Keep reasoning unsupported, with a warning, until the selected control and
  model capability have been validated. It is not a package-wide default and is
  not inferred from the current test account's `gpt-5.6-terra` preference.

### Model capabilities

- Extend account-backed model discovery to retain the server's safe display and
  capability information when present, while continuing to use `slug` as the
  open-string model ID, preserve server order, and include only
  `visibility: "list"` entries.
- Expose a typed, account-aware catalog API. Its documented capability fields
  must distinguish **advertised**, **validated**, and **unknown**; a listed
  model remains not guaranteed to be entitled for a request.
- Report the route-wide constraints already known from research: text and
  mandatory streaming are supported; non-streaming HTTP, Files uploads, audio/
  video, image generation, file search, Code Interpreter, native computer use,
  hosted MCP/connectors, `tool_search`, and persistent Responses state are not.
- Do not advertise model-specific reasoning, tools, images, files, web search,
  JSON schema, or detailed usage support without an account-backed fixture for
  that model/catalog shape. Tools and rich inputs remain v0.4/v0.5 work.

### Provider metadata

- Preserve safe response metadata from received events: response ID, model ID,
  timestamp, request ID, headers, terminal status, and raw usage where present.
- Add namespaced provider metadata for OAuth-specific, non-secret protocol
  facts that AI SDK does not otherwise expose, such as the terminal status and
  any verified reasoning/capability metadata.
- Keep metadata consistent between aggregated and streaming calls. Omit absent
  fields; never expose access tokens, refresh tokens, ID tokens, authorization
  URLs, identity claims beyond existing application-owned context, or request
  bodies containing sensitive data.

### Unsupported-option warnings

- Centralize option handling so `doGenerate()` and `doStream()` produce the
  same request body and warning set.
- Emit AI SDK `unsupported` warnings for each supplied generic or provider
  option that is omitted, including known unsupported Responses fields such as
  `maxOutputTokens`, `temperature`, `topP`, and unsupported rich-output/tool
  settings.
- Do not warn for provider defaults or options that were not supplied. Invalid
  values for a supported provider option fail before making a request; they are
  not silently dropped.
- Never forward fields prohibited by the OAuth plan-sharing route: `background`,
  `conversation`, `max_output_tokens`, `max_tool_calls`, `metadata`,
  `moderation`, `multi_agent`, `prompt`, `prompt_cache_retention`,
  `safety_identifier`, `temperature`, `top_logprobs`, `top_p`, `truncation`, or
  `user`.

### Improved error handling

- Normalize admission, SSE, malformed-event, terminal-failure, premature-EOF,
  and transport errors into redacted `OpenAIOAuthError` values for both paths.
- Preserve HTTP status, diagnostic text (including nonstandard `{ detail }`
  bodies), OpenAI error code, parameter, request ID, and safe retry guidance.
- Classify documented subscription-sharing errors: eligibility, limit, and
  unsupported capability are terminal for the request; temporary usage/user
  availability failures may use bounded backoff; terminal credential/grant
  errors require reauthorization rather than an OAuth loop or billing fallback.
- A stream emits an `error` part and no successful `finish` after it has begun;
  pre-stream admission errors reject the call. A `response.completed` event is
  the only success terminal.

## Non-goals

- Function tools, structured output, images/files, web search, persistent
  response state, retries/fallback billing, browser support, or OAuth lifecycle
  changes.
- A hard-coded model/capability matrix, entitlement guarantee, or a default
  model/reasoning effort.
- Claiming a reasoning request field, reasoning event, or catalog schema that
  has not been validated for the public OAuth route.

## Validation and testing

1. Capture sanitized account-backed `/v1/models` fixtures and reasoning
   request/event sequences for at least one eligible model; record verified
   protocol details and request IDs in `docs/research.md`.
2. Unit- and mocked-integration-test provider-option validation/mapping,
   catalog filtering and capability states, metadata parity, and exact warnings
   for generate and stream paths.
3. Cover JSON and `{ detail }` admission errors, every documented structured
   error category, malformed SSE, failed/incomplete terminals, transport error,
   cancellation, and EOF before completion. Assert secrets never appear in
   messages, metadata, or fixtures.

## Completion criteria

v0.3 is complete when a caller can discover an account-aware capability catalog,
use only verified reasoning controls, inspect safe consistent provider metadata,
and receive deterministic warnings or redacted actionable errors. Unsupported
or unverified capabilities remain explicitly unavailable rather than being
forwarded or implied.
